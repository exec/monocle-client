# Phase 3 operator reliability (draft)

The standalone host's resource mutations require `Idempotency-Key: <UUID>`. Keep the same key, method, URI, `If-Match`, and JSON body when retrying after a timeout. The host journals the command before executing it. A repeated command returns the saved HTTP status and body; changing its intent under the same key returns `409`. Receipts survive a host restart at `GET /v1/operations/{key}`. The journal keeps at most 1,024 receipts and 16 MiB; do not treat a key evicted from that window as safe to replay.

The response includes `operationId` and `correlationId` (both equal to the command UUID). Commands whose worker effect is asynchronous return `202`. Their operation progresses through `host_accepted`, `delivery_queued`, `worker_acknowledged`, and `completed`, or records `rejected`, `superseded`, or `outcome_uncertain`. Queue admission is **not** socket delivery or Minecraft confirmation. `receipt.workers` retains per-worker execution IDs, acknowledgement timestamps and outcome details. A newer request supersedes conflicting intent only for the affected workers; stale control IDs cannot complete it. Configuration uses the exact requested revision. Pending cleanup keeps cancellation unresolved even though the job cancellation decision is immediately authoritative. Authenticated missing-checkpoint reconciliation or cancellation before dispatch can resolve it without replaying actions. Public RWP reports are correlated after existing execution/generation/ownership validation; cleanup reported for inspection remains uncertain.

Both standalone and in-game hosts keep these receipts in their existing task journals. The job inspector shows the latest receipt and per-worker evidence; the in-game task screen shows its summary. A Running Highway action waits for fresh current-generation native building evidence before completing a start/resume receipt. Other workflow starts complete when the worker reports Running or Complete. These are **worker-observed outcomes**, not universal game-server verification. Crew reassignment completes when an authenticated worker is in the requested crew, not when the assignment is queued. Older native clients remain usable, but lifecycle requests other than initial installation cannot be correlated without the updated client.

Original HTTP status/body remain unchanged on an idempotent retry; poll the operation for newer evidence. Synchronous mutations complete and HTTP errors are rejected. If the host is interrupted after journaling intent but before journaling the result, it will not blindly replay the command; inspect its evidence and resource before choosing a new ID. Task journals retain the latest 32 receipts plus unresolved per-worker intents; HTTP receipts have the separate retention window above. Receipt-stage changes are included in the bounded operator event feed.

Crew renames (`PATCH /v1/crews/{id}`) and workflow replacements (`PUT /v1/workflows/{id}`) require `If-Match: <revision>` from the resource's `revision` field. Missing revisions return `428`; stale revisions return `412`. The precondition and mutation are serialized at the host. Other mutation routes do not yet offer revision guards.

Resource-route errors use `application/problem+json` with `type`, `title`, `status`, stable `code`, `detail`, `instance`, `retryable`, and `correlationId`. The legacy `/v1/control` and `/ui/api/*` routes retain their earlier error form.

`GET /v1/events?cursor=<cursor>&limit=100` is a bounded, read-only change feed of the host's operator activity, including command receipts and worker state transitions. `limit` is 1–100. Each event has `id` and `sequence`; the response's `nextCursor` resumes after the returned page. Events are in memory and limited to 128 records, so a host restart, an expired cursor, or a different host session returns `409 event_gap` with `snapshotRequired:true` and a new cursor. Refresh the resource snapshot before continuing. This is polling, not a long-lived SSE connection; job and worker resources remain the source of truth.

Still open in Phase 3: action-specific game-server verification, richer progress and resource-alert events, grant-scoped feeds, and a push stream for consumers that need one. The current host token grants the whole host; fine-grained grants are a later phase.
