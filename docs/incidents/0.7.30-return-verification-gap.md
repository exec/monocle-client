# 0.7.30 returning-worker verification gap

The running 0.7.29 host and workers stalled immediately after Unbans returned from supplies. Execution `65afdbe3-85d1-483b-ac76-196bea9339d6`, job `c3215330-dfd2-4c91-9484-99a7b68b8fea`, origin X -34814, Y 116, Z 0, heading West, endpoint X -50000.

Captured read-only state: job building, generation 0, progress 18, all three active, no supplier or reservation. UnbansBot and UnbansBot2 reported row 18, verification base 19, mask 6 (rows 20 and 21 resolved, row 19 unresolved). Unbans reported row 21, base 22, mask 0, after flying ahead to merge. All were grounded, unpaused, in Forward/crew-window wait, with zero placement and break ACKs and no world wait. This is not the old regroup/world-restoration circular wait.

The return path reanchors logical work to the physical landing row. If a lane transition hands the returner unfinished work in an earlier row, peers cannot advance through that row. The old bounded paving repair only fills replaceable blocks; it cannot excavate clearance or replace incorrect paving material behind the returner. The exact failing cell was not exposed by 0.7.29, so its material/type remains unconfirmed.

Progress subsequently resumed during patch preparation: the last verified checkpoint was 295 (X -35109) when the operator requested a replacement job. The new job `23656ce2-1720-4501-b2fa-e56852130356` starts there, length 14891, and retains the X -50000 objective. This incident therefore demonstrated a prolonged verification stall, not proof of an irrecoverable deadlock. One fully cleaned cancelled history entry was pruned after backing up the job journal to `host-tasks-before-0.7.29-gap-restart.json` in the host data directory.

0.7.30 reuses fresh host window checkpoints and full row verification, filtered to the worker's actual duties, to detect such an owned gap. Only its responsible worker resets logical work to the verified checkpoint and uses normal excavating/paving routines. Physical position, live execution, peer duties, supply recovery and material protections remain intact. No repair is made while local supply/cursor/step recovery or block ACKs are outstanding. The search is bounded to the five-row work window plus the two-block return overshoot; distant stale checkpoints do not order arbitrary retreats. Fully resolved owned cells do not reset a peer.

Worker diagnostics now include the first global and owned checkpoint blocker: coordinates, duty, block ID, loaded/server-state-known status and prediction flag. Recovery logs the physical position and old/new logical work row. This uses the existing window protocol; the 0.7.29 host does not need another restart.

Executable checks cover the reported 21/18 gap, resolved-peer exclusion, stale/out-of-range checkpoints, full-geometry authority versus ownership-filtered repair, and non-retreat/non-restart recovery calls. Live Minecraft validation remains required.
