# Deposit packet before destination opening — 0.13.36

The Zungle → Newstorage multi-kit transfer, task `30676138-c4e1-4f99-89be-b5f81f8f56eb`, failed with **Stash transfer needs inspection: Cannot invoke "net.minecraft.core.BlockPos.getX()" because "this.target" is null** in its native `StashDeposit` action.

Read-only inspection of the worker journal showed 525 kits delivered for the first type and 210 for the current type: **735 confirmed deliveries**, with the latest 35-box load still carried. The failed native action had `elapsed: 0`, `confirmed: 0`, `pending: false`, `touched: []`, and an assigned destination column with `delivery: 2`. Its destination target had not yet been selected. The worker was still at the source coordinates, consistent with waiting for the destination home rather than attempting a destination click.

`BotActions.tick()` waits for home cooldown, warmup and observed arrival before ticking the deposit action. Its inventory event handler remains subscribed during that wait. The shared deposit handler accepted an open menu's full contents without requiring a selected target or requested opening, then passed them to `observeColumn`, which dereferenced the null target. A late source-container snapshot is a plausible trigger; the journal does not identify the exact packet or chest, so that attribution is not proven. The missing guard is independently reproducible.

In 0.13.37, packets cannot enter deposit observation until the action selects a destination, requests opening, and is not waiting for a host acknowledgement. The pre-opening menu is excluded and the first destination menu remains bound even after a click completes. Closing/replacing a menu clears its opening marker and server baseline; only a non-pending transfer may reopen and request fresh column approval. Pending moves still hold position, time out and require inspection instead of being replayed or counted as success.

Offline checks deliver a real container-content packet to the action before reservation, after acknowledgement but before target selection, after selection but before opening, and during an acknowledgement wait. They also check menu binding across clicks and restoration without stale opening ownership. Existing exact-destination, hopper-drain, duplicate receipt and uncertain-restart checks remain active. The new client has not yet been retested live; the recovery job was left untouched during this fix.
