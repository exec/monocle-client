# Stash columns and kits

## Transfers with unread source containers (0.15.35)

Sequential transfers can explicitly set `observedSourcesOnly: true` to collect verified stock from a full, non-lazy source scan that has unread containers. Unknown and inferred records remain unchanged and are omitted from the pickup manifest; confirmed-withdrawal source locations remain eligible for a revisit. Strict planning remains the default. Prepared arguments and final sequential-transfer results include `sourceScanGaps`; a nonzero count prevents the result from claiming the whole source is exhausted. Ender transport is supported; mixed loads and allocated-column rotation are not supported in this mode. This is an operator API option, not a new WebUI control.

## Ender-chest transfer buffer (0.15.17)

Solo sequential until-empty transfers accept `enderTransport: true`; the transfer form exposes this in Drain mode. An empty worker ender chest and a nearby accessible ender chest at each stash are required. The worker opens the nearest loaded ender chest, retries the adjacent same-facing half when a pair opens as 27 slots, and uses the actual server-confirmed 27/54-slot capacity. This version does not place a missing ender chest or enable buffering for crew, mixed-load, round-robin or single-column deliveries.

At source, repeated normal withdrawals fill the ender buffer, then another carried inventory. At destination, normal deposits empty the carried load first, followed by inventory-sized ender withdrawals and deposits until the buffer is empty. With 34 available player slots and 54 ender slots this transports 88 kits, with two ender withdrawals (34 + 20) after the initial carried deposit. Sources advance upward through physically connected chests when necessary; destinations check connected chests downward before asking the host to allocate another compatible column. New columns are existing mapped storage, never newly constructed chests.

Buffer clicks use the existing confirmed transfer bursts without container-close sleep timers. Journal checkpoints retain the phase and expected cargo. Reopening after an interrupted click must prove both matching cargo conservation and the bounded change between ender/player inventories before proceeding. Ambiguous changes stop with cargo retained. Cancelling does not discard ender cargo: resume the original job or empty that cargo before creating a fresh buffered job. Only actual stash withdrawal/deposit actions update stash totals; moving between player and ender inventories does not.

## Storage backend (0.15.0)

Stashes now use SQLite on clients and hosts, with indexed container rows and atomic scan/observation recovery. There is intentionally **no migration** of prior stash data; redefine stashes and start new jobs. Old snapshots, delta directories and queued exports are ignored, not deleted. See [SQLite stash storage](stash-sqlite.md) for the schema, durability, inspection and backup requirements. Historical JSON-journal paths discussed below describe older releases; current passive/solo outboxes and host-summary caches use `sqlite-v1` names.

## Categories and whitelist whispers (0.14.33)

In 0.14.35 whitelisted users can request `kits`, `kits 2`, `kits 3`, etc. by whisper. Each page lists alphabetically sorted raw kit names at the configured minimum complete stock (normally 250), subtracting accepted delivery reservations. Bracketed category slugs tell the user what to put in `kit <category> <count>`; `unlisted` means the stocked kit has no request category. This is recorded stock, not a fresh physical scan. Pages are generated from current stock, so a changing inventory can shift page boundaries. Long individual names are shortened; nonfinal pages end with `,...`. The full `/msg <username> <page>` stays below the client's 256-character limit. Invalid page syntax is ignored; out-of-range pages report the available range. Listing does not start a job or consume a personal cooldown.

Kitbot replies and operator `/msg`, `/tell`, `/w`, and `/whisper` commands share a FIFO capped at one DM per five seconds **per worker**. Duplicate queued texts are coalesced. The queue permits 16 replies per worker and 128 total, discards entries after two minutes or a crew/world change, and waits through temporary disconnects/world loading. It is session-only: a host restart drops pending chat, not accepted jobs or delivery cooldowns. Reported outbound DMs also extend the spacing guard; manually typed or independently issued client-workflow commands are not controlled by this host queue. Public operator chat retains its existing one-second throttle. Queuing/sending is not proof of server delivery.

In 0.14.35 each whitelist entry also supports `maxKits` (**1–36**, default **5**). The host rejects over-cap whisper requests before checking source stock or creating a delivery, and replies with the person's limit. These rejections appear as `LimitExceeded` receipts; they do not consume the personal cooldown, but still participate in the five-second duplicate guard. A lower request can be sent after that guard expires. Caps apply only when accepting new whisper requests: already accepted jobs and manual operator-created delivery jobs remain unchanged. Missing `maxKits` uses five, including legacy entries. Zero cooldown does not disable the quantity cap.

The standalone host owns categories per crew/server/dimension. **Items** rules require nonempty known kit contents made entirely of the specified item IDs; incidental obsidian inside a PvP kit does not make it an obsidian resource kit. **Kits** rules list exact kit IDs. Kits → **Categories & whisper kitbot** edits rules and explicitly seeds stocked categories from a selected stash. Existing definitions and reservations are never rewritten by scans or seeding. Category reservations are available in the column-map dropdown, including shift-selected ranges; category edits wait for active deposits. Updated clients verify actual contents using the host's acknowledged rule. Legacy clients skip category columns rather than mixing incompatible kits.

Whisper requests are an opt-in **standalone-host** feature, not an ingame-host module or RWP requirement. Configure one courier, crew, source stash and a whitelist of exact usernames/UUIDs. In 0.14.34 each person can have their own `cooldownSeconds`; new editor entries default to **one hour**, and **zero disables their quota**. Legacy entries without this field inherit the configuration's shared fallback. The five-second duplicate guard and one outstanding delivery per person remain active even with zero cooldown. Existing request timestamps are retained, so changing a cooldown does not reset history. A request such as `/msg Unbans kit pvp 2` queues a normal low-priority player delivery with return-home enabled; omitted quantity means one, maximum 36. Only incoming `<username> whispers: ...` messages, optionally prefixed with the server's player-head text, are recognized. Whitelisted names are case-insensitive; public lines, outbound echoes, unrelated text, lobby/world-loading messages, and other receivers/servers are ignored. Subsequent requests are ignored during their cooldown, including after reconnect/restart. An out-of-stock or failed request also consumes the cooldown. Unknown categories are out of stock.

Availability requires **at least 250 complete directly observed kits of one exact variant**, minus outstanding accepted requests. Counts are not aggregated across variants to meet the threshold. Inferred upper-chest contents, incomplete kits, ambiguous variants and historical alias totals do not qualify. Delivery may reduce a stocked type below the threshold; subsequent requests then cannot select it. Recorded availability can still be stale if someone else removes stock; the existing courier's verified pickup/handoff decides the actual outcome. Request receipts and job IDs are retained in the panel; acceptance is persisted before submission, and interrupted submissions reuse the same ID. Disabling kitbot stops new requests, not already accepted jobs—cancel those in Jobs.

Operator control operations: `kit-categories-get` (`crew`, `scope`, optional `source` for stock), `kit-categories-seed` (`crew`, `scope`, `source`), `kit-categories-save` (`crew`, `scope`, `expected` revision, `category` with `id`, `slug`, `name`, `mode`, `members`), `kitbot-get`, and `kitbot-save` (`expected` config revision, `config`). `PUT /v1/stashes/{id}/column-reservations` accepts `columns` plus **either** `kitTypeId` (empty clears) **or** `categoryId`, with existing revision/idempotency guards. Native worker checkpoints advertise `kitCategoriesProtocol: 1`; deposit acknowledgements optionally include `columnCategory`.

Server whisper text is **not cryptographic player authentication**: this feature trusts the connected worker and server/plugin to report truthful incoming chat. [Mike](kitbot-mike.md) is an optional standalone-host Ollama handler for natural-language requests; exact commands still work without a model. Neither path exposes arbitrary chat-command execution, a gear locker, or proof that the recipient picked up dropped kits.

## Player couriers (0.14.30; inventory bursts in 0.14.32)

From 0.15.8, category definitions optionally include `usage: "Storage"`,
`"Kitbot"`, or `"Both"` (the legacy default). **Used for** in the category
editor chooses whether a rule organizes columns, names whisper requests, or
does both. A kit can match a broad storage category and a specific kitbot
category independently. The sorting preview excludes Kitbot-only rules and
whisper listings/requests exclude Storage-only rules. Existing reservations
remain valid, regardless of a later usage edit; no stock is moved by editing
categories. The catalog limit is 128 rules. See [sorting](stash-sorting.md).

From **Kits → Deliver** (also available under each stash), select a worker, quantity and recipient username. **Return to source stash after delivery** is enabled by default; the full job editor exposes the same option. The recipient must accept `/tpa`. The public operator API can request `destination: "Player"`, `recipient` (UUID), `recipientName` and `returnHome: true`; the source catalog prepares the worker-specific return route rather than trusting arbitrary return coordinates from the form.

Arrival is confirmed by seeing the recipient within four blocks in the loaded world, including after cross-dimension teleports. An already nearby recipient can satisfy the action without issuing TPA; an issued request still observes its warmup. The courier captures that player's position and facing once, checkpoints it, prefers a supported spot three blocks in front, and checks fallback side positions when necessary. It never chases a moving recipient. Each segment of the walking corridor and the actual next movement is checked for support, collision and hazards, with a 0.12-block/tick handoff speed cap. No supported route within the local area means no drop. The short handoff times out after 600 active client ticks, excluding loaded-server pauses.

In 0.14.32, Drop Items throws directly from matching inventory slots in bursts of up to four clicks per tick, using the existing stash packet budget. Each batch is checkpointed before emission; source stacks, cursor and menu are checked before each packet. Exact server snapshots must confirm every selected source change and the total removal before any batch is counted as delivery. The next batch waits for this confirmation. Partial stacks use vanilla's one-item or whole-stack throw, never rounded-up quantities. The player's own Inventory screen can stay open; foreign containers and held cursors block emission. Uncertain batches are never replayed. Issued 0.14.31 hotbar staging intents still reconcile through the legacy swap path, without counting staging as delivery.

The first approach planner uses short, directly supported corridors on approximately the same level, not a new general-purpose walking pathfinder. It prefers stopping and returning over descending ledges or detouring through unknown terrain. The courier turns toward the captured position and chooses a pitch using the vanilla 26.2 throw velocity, gravity and drag. It sends the facing packet before the native inventory throw. Random throw scatter, server changes and pickup by bystanders remain possible: **delivered means server-confirmed inventory removal, not proof that the recipient collected it**. Issued uncertain drops retain their durable confirmation/no-replay guards, including during failure cleanup and reconnect.

With return enabled, the workflow visits the source stash before reporting completion. It reuses the worker's configured `/home`, cooldown, warmup, source dimension and proximity checks; it can skip `/home` when already within the source's existing nearby threshold. In newly captured 0.14.34 workflows, a failed TPA or safely settled failed handoff returns and redeposits only the delivery's undelivered kits, using existing host column reservations and server-confirmed deposit receipts, then reports an unsuccessful delivery. Already delivered quantities are never restocked or reported twice. An unsafe return, uncertain drop or unverified deposit still needs attention. Updated clients recognize the exact server `Player not found!` response within ten seconds of an issued TPA; public chat and unrelated late messages cannot abort it. Other outcomes retain the existing warmup/timeout guards. Explicit cancellation stops the job, rather than initiating an unrequested return trip. Updates require a newly captured workflow; older in-flight packages remain immutable.

This first courier pass does **not** secure the bot's inventory/equipment in a gear locker. Use a disposable or deliberately equipped worker for risky deliveries. Gear-locker recovery and observed recipient pickup are later work. Explicit whitelist whispers and persisted requester cooldowns are available on the standalone host in 0.14.33; optional natural-language classification is described in [Mike](kitbot-mike.md). No `/kill` or respawn automation is issued.

**Optional stash mending (0.14.29):** when XP is absent and no nearby registered cache or carried personal XP box is available, stash jobs defer mending while their equipped elytra has at least 64 durability remaining. Diagnostics expose `stashMendDeferred`; adding XP resumes the configured repair cycle. Below that takeoff reserve, a synchronized, cursor-clear native inventory handoff lands and swaps to the healthiest usable loose inventory elytra, preserving the worn one. Bound equipment is not removed and shulker kits are not opened for spares. Food shortages, uncertain issued withdrawals and malformed cache records still fail; the final glider's 64-durability takeoff and 32-durability landing reserves are unchanged.

**Stalled maintenance (0.15.42):** if 200 maintenance ticks produce no elytra repair, workers with at least 64 durability continue cargo work and retry after 1,200 player ticks. This backoff spans native action handoffs and is ignored below the takeoff reserve. The log records remaining durability, bottle count and Auto Mend status; a stalled final glider below reserve still stops safely. Bottle use temporarily applies the downward client pitch as well as server rotation, so a preceding queued rotation cannot redirect its item-use packet.

**Covered sources and recovery approaches (0.15.43):** withdrawals reuse the scan/deposit solid-lid check before travelling or opening. A blocked chest advances to another connected chest or source without recording emptiness; deferred contents remain unresolved. Outstanding inventory clicks still reconcile first. Flight clearance consults the active container even after recovery clears its cached route target, preserving collision-checked final approaches during chest interaction.

**Unread sources (0.14.9):** until-empty solo carried-kit transfers skip a source for the current pass when movement, opening or initial contents stall for 200 ticks. Confirmed kits remain in the batch and later sources are tried before depositing. The workflow revisits unresolved sources with its existing bounded retry policy; it must not declare them empty. Unconfirmed clicks or held cursors still require safe reconciliation, not blind replay. This worker-side fix also applies to existing compatible jobs without replacing their scripts.

**Mixed loads (0.14.8):** solo Transfer Stash Kits jobs can set `mixedLoads: true` with 2–16 explicit `kitTypeIds`, one source and one destination stash. Both host job editors expose this as Mixed loads. A short pickup tries the next selected type with the remaining server-confirmed inventory budget before returning to deposit. Each type uses its existing verified native pickup/deposit and destination-column reservation; personal boxes are protected, receipt totals are per type, and each source still needs two empty verifications. This does not intentionally collect unselected kits. Start without carried matching kits; explicit carried recovery remains a separate job. Existing full/non-lazy scan and 54 matching-source-container-per-type bounds apply. Host and worker updates and a newly created job are required; in-flight scripts remain unchanged.

Historical hopper source picks now follow enabled, in-bounds output links to the actual receiving chest before resolving its physical column. That includes a hopper feeding a single independent chest, not only multi-chest stacks. Receipt coordinates and slots reflect the opened chest. Locked, cyclic or unverifiable outputs retain direct hopper reads. This is live topology plus verified inventory observation, **not** a simulation that claims to know closed-container contents or how other players changed the flow.

**Inventory filling during pickup (0.13.73):** if a new item consumes a previously free slot after confirmed kit withdrawals, collection ends that partial batch and uses the normal delivery or ender-chest loading path. The source cursor and original requested load size are preserved for the next trip; a full inventory is not source exhaustion. No unrelated item is discarded by this recovery. An inventory with neither confirmed pickups nor recognized incidental kits still requires space, and uncertain clicks retain their safety checks. Update the client; existing workflow scripts already accept positive partial loads.

Incidental-kit side-deposits currently apply to the ordinary single-worker Kit Delivery / Transfer Stash Kits workflows, including alternating routes. The separate leased three-worker crew-transfer coordinator keeps its existing one-type barrier behavior; it does not enable automatic incidental discards or side-deposits.

**Incidental kit handling (0.13.63):** fresh stash-to-stash plans capture known kit IDs from the source and destination catalogs. While collecting the requested type, the worker retains newly acquired recognized extras and keeps filling remaining slots. The workflow deposits the requested load, then those extras through separate normal column reservations at the same destination stash; locked requested-kit columns do not apply to extras. Extra deposits have separate receipts and do not inflate requested-kit counts or mark a full inventory as source exhaustion. Newly acquired shulkers not recognized by either catalog are discarded and verified before pickup continues. Pre-existing shulkers are protected by their observed name/color/content counts, including matching personal kits during extra deposits. Old plans lacking recognition metadata never discard automatically. Update **host and client**, then create a new job: captured scripts/plans are immutable. This 0.13.63 behavior originally used name/color IDs; 0.13.69 adds the content-aware variants described below. Full selected columns, uncertain item transactions and exhausted destination capacity retain their existing safeguards.

An incidental shulker can also occupy the chosen pickup slot while the ordered source/destination clicks are in flight. After a bounded reopen, a fresh server menu may prove the requested-kit count stayed unchanged, the cursor is empty, and every inventory change is a new non-requested shulker in a previously empty slot. That evidence permits reselection, not a claimed requested pickup or a blind replay. Removals, unrelated non-shulker mutations, expected-kit gains and held cursors still block this recovery path. Interrupted discard checkpoints do not replay destructive actions.

**Unapplied pickup deferral (0.14.23):** until-empty carried-kit transfers move on to other source candidates after two reopens prove the attempted pickup unapplied. The fresh server menu, matching local contents and empty cursor must still satisfy the existing cargo reconciliation rules. Confirmed receipts remain unchanged; the troublesome source is logged and returned as deferred, never cached as empty or reported exhausted. Fixed-count pickups, ender-chest stocking and crew-local leases retain their existing guards. A genuinely uncertain pickup still stops safely; old interrupted pickup checkpoints are not automatically waived. Update the client; no host or captured-workflow change is required.

**Missing pickup responses (0.14.26):** if no full inventory response arrives within 20 client ticks of a single-kit click, an empty local/server cursor and the retained original inventory baseline permit a read-only source reopen. The newly opened server menu must still positively confirm the kit gain or prove the click unapplied before reselection; silence alone never clears a pending click or creates a receipt. This shares the existing two-reopen budget and deferred-source policy. Missing authoritative inventory after reopening, ambiguous cargo and interrupted pending checkpoints remain guarded. No host or workflow update is required.

**Consumable synchronization (0.14.27):** stash maintenance waits for the exact current player's full inventory snapshot before deciding that food or XP is unavailable. Reconnect/respawn clear this evidence; loaded chunks alone do not authorize a shortage. Missing snapshots request the existing no-op inventory resync while the cursor is clear. Food counting includes the offhand once and follows Auto Eat's named-food and blacklist settings. A personal supply request that is no longer needed cancels before travelling or withdrawing; an issued withdrawal must still reconcile, and any intentionally placed cache remains registered for later use. This does not change world readiness or Lobby Skip. Shortage details include inventory readiness and the carried/offhand resource counts.

**Empty-source lifetime (0.14.28):** physical empty-chest hints belong to the current worker task, not one pickup action or connection. A `/home` handoff, temporary host disconnect, pause cleanup or resume of that same task keeps them; accepting a different task clears them. Hints remain server/dimension-scoped, limited to 4096 entries and expire after 30 minutes. A cache-only zero-result search still performs fresh verification, and mixed or changed hopper connections retain their existing conservative checks. Client/process restart starts with an empty cache; this is not persistent stock accounting or proof that external players cannot refill storage.

**Stash travel retries (0.14.24):** if a sent `/home` has not reached the intended stash after its configured warmup plus 60 seconds of arrival grace, the worker retries through the normal cooldown gate instead of terminating after three attempts. A pending travel retry does not trigger the generic stall pause, but no chest work is allowed until dimension/location arrival is verified. A reconnected worker also records observed arrival for cooldown timing; ordinary already-local trips do not consume a cooldown. The existing bounded diagnostic count saturates at `3+`, and cancellation still stops further sends. A wrong home can keep retrying until an operator corrects or cancels the job; inventory, food and durability safety failures remain enforced.

**Empty-column inspection (0.14.24):** until-empty carried-kit transfers allow up to two hopper cycles at an empty bottom outlet, then inspect upper chests without additional per-chest refill waits. If no matching stock is found, they reopen the outlet once and wait out the remainder of the original full, TPS-adjusted propagation window before declaring the chain empty. Travel/inspection time overlaps that window; it is not a shorter emptiness proof. Checkpoints retain the final-outlet obligation but restart its tick clock conservatively. Other pickup policies, crew leases and deposit drain waits are unchanged. Install updated clients; no host or workflow migration is required.

**Interrupted deposit recovery (0.13.62):** connection-loss checkpoints with a pending kit deposit resume instead of failing solely because the click was unverified. Confirmed deposit receipts are retained, but the worker renews host column authority and opens a fresh menu before reconciling complete server inventory, local inventory and an empty cursor. It then deposits only the matching boxes still carried, using new exact server-confirmed source/destination slots. The old click is never replayed. Any unverified box already absent from inventory is logged through the existing shortfall path, not claimed as a successful deposit; hopper movement prevents attributing it retrospectively. Another disconnect preserves the recovery gate. Existing live-click retry/verification remains strict, and uncertain **pickup** checkpoints still require inspection. This also supports older pending-deposit snapshots; update workers, not the host or captured workflows.

**Withdrawal reconciliation (0.13.58):** pending pickups hold position and can reopen the same source after 20 ticks, at most twice per unsuccessful pickup. Only a different, server-confirmed menu showing unchanged player inventory and an empty cursor permits reselection from current source contents; hopper changes do not force replay of the old slot or falsely exhaust the source. Closing an exact held kit can return it to another empty player slot. A fresh snapshot must prove exactly that kit gain, the rest of inventory unchanged and cursor empty, before counting it. Ordinary sources also need source removal or prior exact held-kit evidence. Old-menu packets, wrong kits, unrelated inventory changes and uncertain receipts cannot authorize replay. Reselection retains the retry budget; confirmed receipts are counted once. Pending restart checkpoints still require inspection. Diagnostics retain transaction and recovery evidence. Update clients; no host or workflow update is required.

**Deposit reconciliation (0.13.57):** after 20 ticks without a receipt, a pending kit move can close/reopen the same destination chest, at most twice per kit. The server snapshot must show either an unchanged inventory/empty cursor or the exact kit held on the cursor with its source slot freed before a controlled close. After reopening, replay requires the original inventory restored (allowing only the held kit's return to another previously empty slot), an empty cursor and destination, and compatible column contents. Late packets from the previous menu cannot authorize replay. A freshly observed exact destination receipt can complete the original move instead. Depletion without that receipt remains uncertain, not deposited or missing. Failure diagnostics preserve source/destination slots, carried/cursor counts, snapshot timing and recovery attempts in telemetry, plus structured evidence in the worker journal and client log. Pending moves still cannot replay from a restart checkpoint. Update clients; the host and packaged workflows need no change.

**Upper-source fallback (0.13.56):** when a hopper-fed outlet has no matching kit, withdrawals wait at most 16 ticks if it is empty, or skip waiting if it contains only unrelated stock. They then check the next connected chest upward, continuing bottom-to-top. Checked-empty/non-matching chests are skipped for the current native pickup action, including after checkpoint recovery; a later batch can recheck for newly supplied stock. Live links, stash bounds and unchanged server-confirmed inventory moves still apply. Lost connections or unrelated items that may strand requested kits inside hoppers retain an unresolved-source receipt. Crew plans leasing one specific chest do not expand their lease. Deposit routing and its longer hopper-drain window are unchanged. Update the client; no host restart or scan rewrite is needed.

**Single-column delivery (0.13.54):** operator API/workflow callers can add `targetColumn: {x: 128, y: 64, z: -96, axis: "X"}` (synthetic example) to a **Kit Delivery** stash-to-stash request. Coordinates identify the observed bottom chest of the desired destination column, not the source. The prepared `targetStash` retains this limit. Both host adapters reserve only that column, and the worker independently rejects another selection. Existing observed incompatible stock rejects preparation; changed or mixed live stock stops safely without overflow. Without this option, ordinary transfers keep allocating additional eligible columns.

A selected full column ends the single-kit workflow with `columnFull: true`, verified `delivered`, genuinely `missing`, and still-carried `retained` quantities. It stops taking more kits without claiming source exhaustion. The final batch may leave up to one inventory load on the worker; nothing is discarded or counted as deposited. This uses live chest contents, not a guessed remaining-capacity total. Checkpoints preserve the result and never waive an uncertain inventory click. Update host and client, then prepare a new job; old hosts selecting another column are rejected rather than silently overflowing. This option is not yet exposed as a WebUI checkbox, and multi-kit/crew-transfer jobs do not support it.

**Deferred-source cursor (0.13.54):** after a full batch, a deferred mixed hopper outlet does not end the delivery sub-workflow while unvisited candidates remain. The next pickup continues from its saved cursor. Exhausting the candidate list still returns the deferral for bounded parent retries; direct upper-chest fallback and filling a partial load across separate prepared plans are not implemented by this change.

On **0.13.43**, if requested kits are no longer carried (for example, manually placed or deposited), a server-reconciled destination snapshot with no pending inventory click ends that batch with a logged shortfall and continues the workflow. Receipts and checkpoints retain separate `deposited` and `missing` counts; only verified moves count as delivered. Uncertain clicks are not waived. Update the host and start fresh jobs for the revised workflow accounting; existing jobs keep their packaged scripts.

Save a stash definition with its `/home` name and cuboid even if you do not scan it. In Stash Manager, **Column Map** opens only the bottom chest layer. Its contents identify each column; upper chests are assumed to contain the same kind of stock, but their quantities are unknown. **Full** scans the cuboid and retains the existing optional Lazy Mode estimates. Only directly observed shulkers contribute to exact kit counts.

On **0.13.48**, fresh scans sweep rows along the cuboid's longer horizontal axis. Each row starts from its nearer end, snaking back and forth instead of returning to a fixed edge. The bounded 64-container queue stays within that row; empty rows can be discovered without a separate waiting tick. Layers start from the nearer side while retaining bottom/top/down ordering. Scan telemetry identifies `Nearest-end rows` versus `Legacy raster (resumed)`: pre-upgrade checkpoints retain their original discovery order to avoid missing or duplicating containers. Walking goals are checked every tick; opening, menu settling and durable observation acknowledgement still hold movement, and hidden scan menus need not appear on screen.

On **0.13.49**, fresh **Full scans with Lazy Mode off** instead group neighboring rows and heights into four-by-four cross-sections, sweeping along the longer horizontal axis and snaking between sections. Chests and hoppers enter the same bounded candidate window; reachable containers are preferred before traveling, and the window may cross section boundaries. Initial orientation starts from the nearer ends, including height. This removes separate chest-versus-hopper sweeps in favor of spatially grouped work, without parallel menu opens or duplicate coordinate discovery. Column Map and Lazy Mode retain the 0.13.48 strategy. Telemetry reports `Nearby container bands` for the new order; older checkpoints retain their old traversal, so start a fresh scan after updating to use it. Both solo and worker-controlled scans share this code; no host update is required.

On **0.13.69**, color (item ID) and literal custom name define a kit family, not a unique kit. Observations with unrelated item contents get distinct **Shulker Type IDs** within that family. Quantities are not part of the ID, so lower-count copies remain incomplete rather than becoming new types. The fullest observed related box becomes the exemplar; missing exemplar items or quantities count as incomplete. Observed item overlap is a heuristic, not semantic kit categories: overlapping contents can still classify together. Truly empty boxes have a separate type instead of being guessed to belong to a depleted full kit. Unknown contents never match a kit. Copy the ID from stash inspection; raw custom names are not renamed.

Legacy name/color IDs are retained as aliases to their old fullest exemplar's type. Existing reservations and captured requests remain resolvable; unrelated historical boxes are reclassified on load without changing their saved quantities. A read-only migration does not rewrite the snapshot; its next catalog mutation checkpoints the new index. Fresh plans carry compact validated `kitIdentities` descriptors where needed so the worker uses the same classifier for actual pickup, incidental handling and deposits. A host-owned deposit plan links compatible independently learned source/destination IDs and preserves a type first learned incomplete when full boxes arrive. Captured older plans fall back to their exemplar; create new jobs after updating host and workers for complete new metadata. Incoming observations are classified by the catalog, never by a worker-supplied ID. The WebUI chest-location view and column map use assigned type IDs rather than name/color alone; ambiguous unindexed legacy contents remain uncertain.

For operator comparisons, prefer the standalone host's `GET /v1/kits/{kitTypeId}/stock` [reporting endpoint](workers-api-v1/phase2-operator.md#comparing-kit-stock-between-stashes). It resolves aliases and reconstructs same-name/color family variants from recorded box contents. Different TSR Redstone versions no longer appear absent or become incomplete merely because a merged catalog exemplar changed. Partial boxes compatible with several versions are marked ambiguous; unknown contents remain separate. Reporting signatures are not necessarily assignable kit IDs. These are recorded estimates with coverage metadata, not a new scan or a change to transfer matching. Overlapping stashes must not be summed.

The built-in **Kit Delivery** and **Remove Incomplete Kits** workflows use one worker per job. Supply a source stash, Shulker Type ID, and count (1–36). A destination can be a player (exact UUID and username, who must accept `/tpa`), a nearby ender chest, another defined stash in the same world, or the worker's carried inventory. Incomplete removal defaults to carried inventory; select a separate destination stash to quarantine those boxes. The worker first takes boxes observed in the scan, then searches unscanned upper chests in mapped columns as needed. An unscanned column is a search hint, not a stock guarantee.

**Transfer all** is available for stash-to-stash jobs on workers running 0.13.17 or newer. Enable it in the WebUI kit job form or in-game host task editor; the count becomes the per-trip cap (up to **36**). The equivalent workflow arguments are `transferAll: true`, `count: 36`, `destination: "Stash"`, and `targetStashName`. `includeIncomplete: true` optionally includes incomplete boxes of the same type. Incomplete-removal jobs cannot include complete boxes.

Repeat transfers require a **Full** source scan with Lazy Mode off and no inferred/unknown container records. On 0.13.26, a known location invalidated by our own confirmed withdrawal can be searched again without pretending its quantity is still current. They check every selected matching source container live, revisiting it until empty before advancing; hoppers and other scanned storage containers are supported. ## Live storage observations (0.13.65)

**Stash Manager → Live storage updates** is enabled by default and works even when the module is inactive and no job is running. It passively observes storage inside already defined stash cuboids. It never opens a chest, moves the player or changes inventory. The existing **Export to host** switch also controls these updates; solo observations stay local when export is off.

- Opening a mapped container manually or through a native job binds its actual interaction coordinates to the server's menu. Full contents and subsequent container-slot packets are coalesced after two quiet ticks or when the menu closes. Client-predicted clicks are not evidence. Items added/removed by other users or hoppers are visible while the server sends contents for an open menu; closed-container contents are not magically readable.
- Server block/chunk observations discover new storage and retire missing storage. New unopened chests contribute physical capacity, but their contents remain **unknown**, not empty. Open them or scan them to establish free slots and make them eligible for automatic allocation. Expansion outside the saved selection requires extending its bounds first.
- A confirmed missing/replaced container becomes `status: "removed"`, retains an audit record and is excluded from resource totals, capacity, column maps and future source plans. A break attempt alone, unloaded chunks or a storage block whose metadata is still loading cannot establish removal. Another worker can report destruction by anyone; identical observations are deduplicated rather than relying on one designated breaker being online.
- Double chests use one canonical physical record with both halves and actual capacity. Merged aliases are retired. Removing one half reconciles the remaining half without counting both the old double chest and the survivor. A changed shape invalidates contents until a fresh menu read; unchanged geometry enriches legacy scanned records without erasing their stock.
- Scans reconcile known coordinates encountered in loaded regions, including those now missing. This is **positive reconciliation**, not a wipe-on-rescan: failed reads, missing chunks and omitted upper rows in a column scan cannot erase stock by omission.

Observations are atomically saved on a background writer, coalesced per container and retained in `stash-live-outbox.json` before host delivery. On **0.13.71**, supporting hosts advertise `stashLiveBatchProtocol: 1` in the native stash catalog. A worker uploads up to **32 updates** in `task-stash-live-batch`, receiving independent results in `task-stash-live-batch-ack`. Both frames and the total expanded observation payload are capped at **64 KiB**. Each entry retains its event ID and compare-and-set hash; durable per-entry commits precede acknowledgement, and a committed prefix is safe to retry if a later storage write fails. This is batching, not a cross-stash transaction. Malformed envelopes are rejected before applying entries; bounds and crew authorization remain enforced by each catalog update.

Only the current negotiated connection enables batching. Older hosts and a contents read too large to fit the batch retain single-update delivery. Retries reuse event IDs, partial ACKs clear only their events, and newer queued snapshots survive disconnect parking. The flat `stash-live-outbox.json` recovery format remains compatible. The bounded outbox permits 256 events and 3 MiB of queued payload. If it fills, the client warns that uncaptured updates need a rescan; it does not block game movement or inventory. A world change parks old-world updates and permits observations in the new world. Queued host updates are scoped to the host endpoint and credential identity, so they are not uploaded to another host.

On **0.13.72**, chunk arrivals only enqueue passive discovery. Catch-up uses a per-chunk coordinate index, merges overlapping watches' candidate positions, and physical reconciliation processes at most 32 coordinates per tick with a two-millisecond between-record budget. A single coordinate, chunk enumeration or journal snapshot can still exceed that time; this is pacing, not a frame-time guarantee. Unchanged geometry is checked against pending and in-flight reports as well as acknowledged records, preventing duplicate uploads and downgrading queued contents during repeated discovery. Exact queue-size checks cache immutable entries instead of repeatedly serializing the entire queue. Real shape changes, loaded missing coordinates and server-confirmed contents still update normally; no scan is required merely to learn a new chest's capacity.

The host compares the container revision the worker observed before accepting an update. A stale snapshot/removal cannot overwrite newer accepted contents. Conflicts are logged and discarded, with current geometry returned; reopen or rescan to refresh disputed contents. Deleting a stash retires queued updates instead of recreating it. The latest 256 physical lifecycle events are retained in `containerEvents`; this is bounded history, not a full inventory transaction ledger.

On **0.13.66**, a stash supports up to **16,384 container records**, including hoppers and removal tombstones. The 1,048,576-block selection and 64 MiB journal limits remain; very item-dense catalogs can reach the byte limit first. Scan discovery, checkpoints, receipts and observer pagination use the same container bound. Workers optionally advertise `stashContainerLimit`; both host types keep 32-record frames and omit an entire oversized live baseline for older workers (legacy limit 4096), never truncate it. Update host and clients for large stashes. Chunk catch-up defers physical observations while the upload outbox is full; menu snapshots retain the existing bounded queue and warning behavior. New unopened containers still require a contents read before automatic allocation.

Revision-checked stash edits can expand observed bounds outward without clearing stock or column reservations. Shrinking or moving an observed selection still requires a separate definition. Old scan/live observations do not overwrite the current definition or undo a newer /home setting. Changing bounds clears full-column hints because added rows may provide more space; active transfers capture destination bounds and should be restarted after expansion. **0.15.21:** a replaced or closed ender-cargo menu preserves all issued clicks and reopens for reconciliation. A replacement snapshot arriving first follows the same path. Counts across inventory and ender storage plus the exact cargo fingerprint must agree before continuing; the worker cannot replay uncertain moves or retire their checkpoint as ordinary finished history. Reopening retains the existing three-attempt bound.

**0.15.22:** if a deposit slot becomes occupied while the exact picked kit remains on the server cursor, closing and reopening can return it to inventory. A fresh menu must prove that exact kit returned without other cargo changes before clearing the pending move and selecting fresh space. An occupied destination is never credited as a deposit on that evidence alone; normal full-column allocation and incompatible-stock checks still apply.

**0.15.23:** an unlocked deposit receiving `capacityUnavailable: true` lands and asks the host again every ten seconds. Newly observed space or changed reservations can unblock the same job. Accepted findings advance their delivery ID; retries never replay a deposit or discard an uncertain move. The wait survives restart, keeps the normal reservation rules, and does not affect explicit single-column stops. A fully confirmed final deposit completes without requiring another column. Both host and client updates are required; the existing 4,096-finding bound still applies (about eleven hours of uninterrupted capacity waiting).

**0.15.24 allocated-column policy:** operator-prepared sequential transfers can set `fillAllocatedColumns: true`. Each type uses its compatible mapped allocations until no usable capacity remains, then redeposits excess carried kits and drains any ender cargo back into the source through that worker's configured home. It proceeds only after those moves are confirmed. Results separate destination deliveries, source returns and missing kits, and list `destinationLimited` types without declaring Main emptied. This supports ender transport, requires a clean carried-kit start, and excludes mixed loads, round-robin routes and explicit single-column jobs. Incidental kit deposits retain normal capacity waiting. Update both host and client and prepare a new workflow; frozen running packages are unchanged.

Until-empty solo carried-kit transfers also defer a source whose approach makes no useful progress for 200 ticks. This records unread/unresolved contents, not an empty source, advances to other candidates and retains the parent workflow's bounded revisit/failure policy. Chunk-approach stalls follow the same rule. Fixed-count, crew-local and ender-chest loading actions retain their requirements, and no pending inventory move or held cursor can be deferred.

Server snapshots must match a planned completed prefix of the player inventory, have an empty cursor, and prove every newly acknowledged destination's exact item/components. Duplicate/stale replies do not add receipts. A final snapshot can confirm several moves at once only if it still proves all their destinations; missing replies plus drained destinations remain ambiguous. Confirmed pickup/deposit receipts are recorded on packet arrival rather than waiting for another game tick.

A burst still awaiting confirmation 20 ticks after its last issued part closes and reopens its container once. The new menu is an ordering barrier for already-issued clicks, not permission to replay them. If the fresh player inventory matches precisely the known confirmed prefix, the remaining moves are proven unapplied and the action switches to the old single-kit path. That fallback choice survives its checkpoint. Unknown extra changes, a held cursor or inventory loss without a destination receipt cannot authorize retry; the bounded 100-tick inspection failure and existing interrupted-action safeguards remain. Interrupted deposit actions restore into fresh reconciliation; uncertain source/ender-chest moves still require inspection rather than automatic replay. Logs/checkpoints include burst size, mode, verified prefix, slot pairs and menu/state/tick evidence. No host or protocol change is needed. Live testing must establish server packet tolerance and actual transfer-speed gains.

Existing-container flight uses interaction reach rather than printer placement clearance. A three-second no-motion watchdog attempts up to three collision-checked escapes/replans before landing safely and reporting a retained-load failure. Local worker checkpoints include `stashFlight` diagnostics and recovery warnings appear in the client log. These checks are shared by solo scans, withdrawals and deposits as well as coordinated native actions; printer placement geometry is unchanged.

Automated stash cruise flight requires three blocks of clear air around the entire player body, including underneath, overhead and sideways. This is a conservative box buffer, not just a feet-height check. Cruise routes and fresh steering reject any non-air block or unverified/unloaded space inside it. **0.14.17** fixes a conflicting ElytraFly autopilot guard: world build height limits placement, not flight. The actual movement guard now permits the planner's cruise altitude above top-row chests while retaining loaded chunks, collisions, hazards, borders and the lower void boundary.

**0.14.22 cruise:** shared worker stash travel can reach 2.5 blocks/tick (50 BPS at 20 TPS), or the user's lower ElytraFly horizontal-speed ceiling. It uses the module's acceleration settings; step 1.5 with start 0 adds 0.15 blocks/tick per movement update. Braking, corrections, recovery and new travel reset the ramp. The existing full per-tick collision sweep and loaded three-block clearance still apply. Close container approaches, escapes, clearance exits and landing are unchanged. This is a speed ceiling, not a promise of 50 BPS through turns, near containers or under server lag. Install the updated client; no host update is needed.

Takeoff can temporarily enter the buffer while following a bounded, collision-checked upward or sideways exit into clear air. Deliberate landing uses supported-floor checks and is exempt until grounded. On **0.14.17**, final container approaches within the local planner's 32-block radius also use actual swept-body clearance rather than the cruise buffer. Opening holds, eating/server waits, escape recovery and retained-flight handoffs near that target use the same exception, so the clearance maintainer does not pull a valid approach away from the chest. No actual terrain, hazard or unloaded-space check is waived. If no collision-free opening route fits, the action lands before falling back to Baritone. Watchdog diagnostics include approach/cruise phase, cruise clearance, build height and glider durability; equipment failures identify the equipped item. Client update and live verification are required; settings, placement geometry and the 64/32 durability thresholds are unchanged. This is not protection against combat damage or server-forced loss of flight.

**0.14.18 landing:** the shared worker landing probe uses actual collision shapes and fractional surface heights rather than accepting only full cubes. A chest lid or suitable hopper/slab surface is valid only when the entire real player footprint is supported, standing headroom is clear, and the gliding-body descent is collision/hazard checked. Unsupported edges, gaps between separate chests, unread/unloaded support, fluids, portals and damaging surfaces remain rejected. Connected chest halves may jointly support a footprint. Searches remain bounded to 32 blocks downward and nearby landing cells are preferred over a long breadcrumb retreat. Integer-grid walking keeps its full-floor rules. Specific landing status also survives workflow/profile handoffs, so operators see the actual blocked/searching/retreat state. Install updated workers; no host or catalog update is needed, and live validation is still required.

## Crew stash transfer (0.13.38)

Choose **Crew Stash Transfer** (`task-stash-transfer-team`) in saved WebUI presets or the in-game host's Stash Management workflows. Select two or three connected workers, a fully scanned non-lazy source, and another mapped destination. The first selected worker leads; the API also accepts an explicit `leader` UUID. Start without carried matching kits; use solo deposit recovery first if necessary. `count` is the per-worker batch cap, up to 36, constrained by actual free inventory. Kit selection and the existing 54-source-container limit per type are unchanged.

The leader alone uses its worker-specific stash home names, home warmups and cooldowns. As soon as it **sends** `/home`, it checkpoints and immediately reports that event. Followers request `/tpa <leader>` during the leader's warmup, and the host accepts after 10 ticks (500 ms). TPA warmup defaults to 300 ticks/15 seconds and is configurable independently. This overlaps the waits; it cannot guarantee identical arrival times on every server. Some servers snapshot the target's old position. Followers must see the leader in the intended stash area and dimension, not just nearby at the old location. Failed TPAs retry at most twice; incorrect arrivals never permit inventory operations.

Fresh observations of all arrivals gate parallel chest work. Source chests are partitioned so workers cannot race the same inventory; each deposit receives an exclusive destination-column lease, even if another worker disconnects. Workers with empty source shares accompany the group but do not replay a previous batch. The leader's next travel leg starts only after all pickup/deposit results are acknowledged. Each type is searched through two empty passes before advancing; completion reports verified total and per-type deliveries. The host exposes `crewTransfer` with phase, batch/readiness per worker, and totals without exporting internal plans.

```json
{
  "name": "SyntheticSource",
  "targetStashName": "SyntheticDestination",
  "count": 36,
  "leader": "<selected-worker-UUID>",
  "tpaWarmupTicks": 300,
  "includeIncomplete": false
}
```

This workflow reuses native `StashResupply`/`StashDeposit`, their exact-kit checks, uncertainty protection and navigation. The internal `StashVisit` only establishes physical arrival; `KitTransferPlan` is a token-bound barrier with a monotonically increasing step and the preceding native result. Neither action exposes an unrestricted remote inventory command. Pausing does not count against the batch watchdog, cancellation does not release another command, and reconnecting workers must reconcile their checkpoints. Do not remove/replace workers mid-transfer: cancel safely and start a new crew assignment. Update both host and workers to 0.13.38. Offline checks cover the flow; live-server teleport behavior still needs testing.

## Scan persistence responsiveness (0.13.53)

The sequential behaviour described in this historical section is superseded by the scan pipeline below in 0.14.48.

The scanner saves each immutable observation on a bounded daemon writer instead of performing growing catalog reads, serialization and filesystem synchronization on the Minecraft thread. It closes the scan menu and reports **Saving locally** while the write completes; it never advances or uploads before local durability. Failure propagates to the job. A restart while saving retains the old selected target/counters and rereads that container rather than claiming it was scanned. Legacy checkpoints and saved route order are unchanged.

Observation-only catalog ingestion avoids recalculating the complete operator summary on each save. Mutation locking prevents definition and reservation edits from racing background writes. Worker scan checkpoints are forced for new observed/unscanned results, regular recovery intervals and matching acknowledgements, not every Opening/Reading/Confirming display change. Newly checkpointed findings upload immediately, with existing bounded retries and receipt validation. Deposit permission and inventory confirmation logic are not relaxed.

The catalog still uses atomic whole-file JSON replacement, and scanning still waits for one outstanding host acknowledgement. These changes target game freezes and unnecessary CPU/disk work, not a claim that storage or transport can no longer limit throughput. A bounded durable multi-observation outbox and incremental catalog storage remain follow-up work; they must preserve cancellation, reconnect and final receipt drainage. Updating only the client provides the worker-side improvements; update either host adapter to obtain ingestion savings there. No SQLite migration is introduced.

## Pipelined scans (0.14.48)

In 0.15.1, scans can choose a shared opening position for a local group instead of independently approaching every chest. The bounded search samples nearby walking surfaces and, when flight is already active or needed for elevated access, hover positions. Candidates must expose the active container within a conservative 4.2-block eye-to-center radius; actual line of sight and chest-lid availability determine which other unread containers count. Scoring balances coverage with travel cost, not just geometric proximity. Physical double chests remain deduplicated before planning.

The plan considers at most 64 nearby containers and a fixed 343-cell grid, checks at most 48 ranked stance candidates, and fully evaluates visibility for at most eight valid stops. Plans are reused for unread group members and throttled to at most once per ten ticks. Walking uses actual collision-surface support and Baritone's chest-top/slab goal convention; hovering uses checked flight corridors. An unreachable stop is abandoned with a retry cooldown, preserving the existing single-chest fallback. Plans are ephemeral, so resumed scans recheck current world geometry. `coveragePosition`, `coverageContainers`, and `coverageSearchMicros` report the selected group and search cost. Transfers and stock accounting do not use this planner. Live speed and navigation behavior still require testing.

In 0.14.49, full scans enter each spatial band from its nearest long-axis end and finish its queued containers before reversing. Empty bands no longer determine which end of the next occupied band is visited. Existing band checkpoints transition at the next drained band boundary; older raster/row checkpoints retain their discovery order. Scans may walk toward another nearby container during a read, but stop before the current read leaves a conservative 3.5-block eye-to-container range; normal movement safety and buffer backpressure still apply. Transfers are unchanged.

Scanning and host receipt delivery no longer alternate one container at a time. After receiving authoritative menu contents, the scanner closes the menu after one settling tick and may select/open the next nearby container while its background writer and host uploader continue. This remains read-only: the scanner never performs inventory-transfer clicks, mines, or places blocks. Full, column-map and lazy scans retain their existing geometry and quantity semantics.

The bounded pipeline holds at most 32 observations / 2 MiB, eight background writes and eight in-flight uploads. It reserves room for a maximum-sized observation before opening another container. A full buffer pauses discovery until disk or host receipts catch up; observations are not dropped. Only reads whose local catalog/export and recovery checkpoint have completed may upload. The native finding format and contiguous delivery IDs are unchanged. Both host adapters group scan receipts for up to 100 ms (or a full window) and commit task state before sending their acknowledgements. Deposits, withdrawals and courier transactions retain their separate immediate durability/permission paths.

As of 0.15.0, coordinated workers keep this recovery state in the stash database's `scan_checkpoints` table, committing it atomically with each observation off the game thread. The execution/action binding and plan hash must match when resuming. A crash after a host acknowledgement but before the next local commit can replay already accepted reads; hosts re-acknowledge without applying them twice. Normal completion waits for both background writes and every host receipt. Cancellation stops the job without claiming full host coverage; pending results remain retained in its checkpoint/local catalog. Pre-SQLite stash jobs should be cancelled and recreated, not resumed into the new catalog.

Telemetry distinguishes `observed`/`unscanned`/`removed` read outcomes from `durableReads` and `hostConfirmed`. `queuedObservations`, `queuedBytes` and `localWrites` identify network versus disk backpressure. During reading, the movement target belongs to the next container, not the last uploaded one; an acknowledgement never clears that target. Update workers for the pipeline and hosts for grouped receipt savings. Live throughput still depends on server response, movement and catalog I/O; offline checks are not a speed guarantee.

## Solo export durability and definition editing (0.13.67)

Solo scans do not wait on network delivery. When host export is enabled and a host/crew key is configured, the scanner first atomically journals each export under `stash-export-outbox`, then saves local contents and advances. The outbox is scoped to the configured endpoint, credential selector (not the secret key), account UUID and stash world. A later read of the same coordinate coalesces its queued export; full offline scans are not limited to the passive observer's 256-event queue. Disconnects, restarts and stopping the scan retain queued exports. Disabling host export pauses their delivery.

Both host types advertise `stashExportProtocol: 1` in the native stash catalog. Only then does the client send receipt-based `task-stash-definition` / `task-stash-import` messages with an `exportId`. Older hosts leave exports queued rather than receiving unknown messages. `task-stash-export-ack` reports `accepted`, `deferred` (world/report not ready), or `conflict`. The host stores its last receipt per worker/stash with the observation's atomic write; retries of an already-receipted export do not replay its contents. Matching receipts cannot delete a newer coalesced read. Journals are removed only after acceptance; conflicts remain on disk and are logged for review. Reopening/editing and saving a current definition replaces that definition's conflicted export. Filesystem failures remain visible errors, not successful exports.

Catalog summaries now include `definitionRevision` separately from the full stock `revision`. Definition imports compare the revision captured when editing, while normal chest observations do not invalidate it. Workers may update their own `/home` route; host defaults and other workers' routes are preserved. Every definition mutation rejects shrinking an observed selection, including legacy client exports. A captured old scan may still export containers within current bounds without replacing an expanded definition. Remove/redefine a stash intentionally rather than shrinking its existing observed selection.

Home cooldown remains **minutes** in the client setting for configuration compatibility, but now accepts fractional minutes and rounds back to ticks. For example, 16 seconds is approximately 0.2667 minutes, not zero. Passive live updates also checkpoint their journal before applying local catalog changes. These fixes do not change movement, kit classification or transfer scheduling. Update both host and workers; game-backed offline/reconnect scans still need live testing.

## Legacy discovery and observer reloads (0.13.68)

Passive discovery adds compatible physical geometry to a legacy verified observation without replacing its saved items or kits, even if the old scan lacks slot counts. It preserves the contents timestamp and does not invent slot occupancy. Existing capacity or slot-count evidence must agree, and saved kit slots must fit. A change to known physical parts/capacity still makes contents unknown until a real read. Older snapshots remain historical estimates, not a guarantee that nobody changed the chest since scanning it.

Local observer reloads produce compact geometry and CAS hashes on the background writer, reading each selected catalog once. They do not compute operator summaries or overlap deduplication for passive watching, nor hash full chest contents on the game thread. A legacy kit index is migrated on that background path when needed. In 0.13.68 catalogs still rewrote atomic JSON files; 0.13.69 replaces observation writes with the incremental storage below. Update both host types and workers. Live performance and reconnect testing remain pending.

On **0.13.70**, local and outgoing watch baselines exclude historical rows outside the stash's current selection without deleting their saved contents. Legacy definitions missing a valid required home stay in the catalog but do not authorize passive watches until corrected. This prevents old scan approach coordinates or incomplete definitions from rejecting an otherwise valid watch manifest; incoming worker validation remains strict. Updating the standalone host alone corrects its outgoing baselines for existing workers.

## Incremental catalog persistence (0.13.69)

Historical format only: **0.15.0 replaces this implementation with [SQLite](stash-sqlite.md) and does not import these files.**

The existing `stashes/<id>.json` remains a retained snapshot. Observation updates atomically write one bounded JSON delta beneath `stashes/<id>.json.deltas/`, including changed container records, removed aliases and export receipts. Files use the existing UTF-8 byte limits, forced writes and atomic renames. No database dependency is introduced. A checksummed sequence and snapshot-base hash prevent accepting gaps, corrupted frames or externally changed snapshots. Failed writes do not advance the cached state or acknowledge an export; originals remain available for recovery.

The current reader replays deltas on a cold restart. After 128 deltas or 8 MiB of journal data, the next observation commits a full snapshot before retiring old frames. A crash between those steps leaves obsolete frames that the new snapshot epoch safely ignores. Rare definition/reservation edits also checkpoint the full snapshot. The cache keeps at most 32 stashes and returns detached copies. A 16,000-container regression verifies that one observation writes only changed records, while cold replay reconstructs the complete catalog.

**Back up the entire `stashes` directory, including adjacent `.json.deltas` directories.** Copying a snapshot alone can omit recent observations. Older versions cannot replay deltas: do not downgrade against pending journals. Read/export through the current catalog implementation or retain a pre-upgrade backup for rollback. Kit identity migration and incremental persistence are shared by the standalone host, in-game host and solo client catalogs. Neither change alters navigation or item transaction verification. See [audit completion and live-test handoff](stash-management-audit.md).

From **0.15.15**, same-server stash transfers accept `targetDimension` when the
destination is in another world. The source job retains its own dimension;

Full transfers from **0.15.16** can retain up to 1,024 matching source containers

Above 512 sources, positions use numeric `[x, y, z]` triples; workers expand them
only inside the native collector. Older position objects remain accepted.

are rejected rather than silently truncating the source. Ordinary fixed-count

From **0.15.16**, manual reservations can select same-crew kit types from other

From client **0.15.14**, this destination mode also uses an aisle-first deposit

This is a definition flag `bounds.assumeEmpty` (boolean, off when absent), not a fake full scan. Capacity is labeled `assumedEmptyContainers` / `assumedEmptySlots`, separate from observed free space. ## Explicit shared columns (0.13.55)

A locked `targetColumn` delivery may also supply `columnKitTypeIds`, an array of 2–16 distinct canonical kit UUIDs including `kitTypeId`. This opts only that physical column into storing those types together. Its persisted reservation remembers the whole group; each later shared delivery must supply the same group. The original primary kit remains the map label. Ordinary single-kit allocation skips shared columns.

Host and worker both reject unrelated kits, loose items and uncertain contents. A full shared column stops with the existing `columnFull`/`retained` receipt and never allocates overflow. ### Advanced workflow: one column per turn

A `task-stash-transfer` request can provide `columnAllocations`, an object mapping
selected kit type IDs to ordered arrays of destination column descriptors. The
workflow fills one allocated column per kit in `kitTypeIds` order before beginning
the next round. Allocating adjacent columns keeps each kit grouped spatially.
This mode uses inventory transport and returns overflow to the source before
switching types; it cannot be combined with ender transport, mixed loads, routes,
or deposit-first recovery. Exhausted sources leave the rotation. Unavailable
sources and allocations with no further usable columns are reported separately
in the final result rather than being claimed as verified source exhaustion.
